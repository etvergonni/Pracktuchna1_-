## Завдання для звіту

### 1. У чому полягають ключові відмінності між class і struct?

Клас (class) - це посилальний тип (reference type), а структура (struct) - тип-значення (value type). Це і є головна відмінність, з якої випливає решта.

Об'єкт класу зберігається в керованій купі (heap), а змінна містить лише посилання на нього. Структура зберігається там, де оголошена змінна: на стеку або всередині іншого об'єкта, без окремого виділення в купі. При присвоєнні клас копіює посилання (обидві змінні вказують на той самий об'єкт), а структура копіюється повністю (створюється незалежна копія всіх полів). Класи підтримують успадкування, структури - ні (але можуть реалізовувати інтерфейси). Класи можуть мати значення null, структури за замовчуванням ні.

### 2. Коли доцільно використовувати структури, а коли класи?

Структури доцільні для невеликих, простих, незмінних даних, які представляють одне значення: координати, грошова сума, оцінка, комплексне число. Орієнтир: структура маленька (зазвичай до 16-24 байт), логічно є єдиним значенням і не потребує успадкування. Це зменшує навантаження на купу і збирач сміття.

Класи доцільні для великих або складних об'єктів зі змінним станом, поведінкою, потребою в успадкуванні чи поліморфізмі, а також коли об'єкт має спільно використовуватись за посиланням. У роботі Student залишається класом (велика сутність зі станом і поведінкою), а легка копія його ключових даних винесена у структуру StudentRecord.

### 3. Що таке readonly struct і які переваги він дає?

readonly struct - це структура, у якій усі поля незмінні після створення. Компілятор гарантує, що жоден метод не змінює стан структури. Переваги: незмінність робить код передбачуванішим і безпечнішим (значення не зміниться випадково), компілятор може ефективніше працювати з такою структурою, уникаючи зайвих захисних копій при викликах методів. У роботі всі структури (Point, GradeRecord, StudentRecord, ComplexNumber, Money) оголошені як readonly struct, бо вони незмінні за задумом.

### 4. Наведіть приклади реалізації Equals(), GetHashCode() та IEquatable<T> у ваших структурах

Кожна структура реалізує інтерфейс IEquatable<T> (типобезпечне порівняння без упакування) і перевизначає Equals(object) та GetHashCode(). Приклад зі структури Point:

```
public bool Equals(Point other) => X == other.X && Y == other.Y;

public override bool Equals(object? obj) => obj is Point p && Equals(p);

public override int GetHashCode() => HashCode.Combine(X, Y);

public static bool operator ==(Point a, Point b) => a.Equals(b);
public static bool operator !=(Point a, Point b) => !a.Equals(b);
```

Типізований Equals(Point) уникає упакування і приведення типів. Equals(object) потрібен для сумісності з загальним механізмом порівняння. GetHashCode через HashCode.Combine узгоджений з Equals: рівні структури дають однаковий хеш, що важливо для роботи у словниках і множинах.

### 5. Які результати ви отримали при порівнянні продуктивності struct vs class? Проаналізуйте їх

Клас PerformanceTest створює масив структур StudentRecord та масив класів Student (по 50 тисяч елементів) і вимірює час заповнення, сортування, пошуку та споживання пам'яті.

Заповнення масиву структур стабільно швидше, бо елементи лежать суцільно в одному масиві без окремого виділення кожного об'єкта в купі. Масив класів повільніший на заповненні, бо для кожного студента виділяється окремий об'єкт у купі. Структури також споживають менше пам'яті на службові дані і менше навантажують збирач сміття, оскільки не створюють тисячі окремих об'єктів. На сортуванні й пошуку різниця менша, але структури не програють. Висновок підтверджує теорію: для великої кількості простих однотипних даних структури ефективніші.

(Конкретні числа залежать від комп'ютера, фактичні значення наведено на скриншоті роботи програми.)

### 6. Як інтеграція структур вплинула на вашу систему?

Інтеграція дозволила швидко й дешево копіювати ключові дані студента без створення повноцінного об'єкта: метод Student.GetRecord() повертає легку структуру StudentRecord. У StudentGroup частину даних переведено в масиви структур: лабораторні місця (Point[]) та історію оцінок (GradeRecord[]) через метод OptimizeStorage(). Це зменшує кількість об'єктів у купі і навантаження на збирач сміття при роботі з великими обсягами однотипних даних, не змінюючи основну логіку системи.

### 7. Які труднощі виникали під час роботи зі структурами?

Перша трудність - правильно реалізувати рівність. Недостатньо перевизначити лише Equals: для коректної роботи у колекціях треба узгоджено перевизначити Equals, GetHashCode і оператори == та !=, а також реалізувати IEquatable<T> для уникнення упакування. Усе це зроблено для кожної структури.

Друга трудність - пам'ятати про семантику копіювання. Оскільки структура копіюється за значенням, зміна копії не впливає на оригінал. Тому структури зроблено незмінними (readonly struct), щоб не було плутанини з тим, де копія, а де оригінал.

Третя трудність - вимірювання продуктивності. Щоб числа були чесними, перед замірами пам'яті викликається GC.GetTotalMemory(true) для актуального стану, а заповнення, сортування і пошук вимірюються окремо через Stopwatch.

### 8. Що нового ви дізналися під час виконання цієї практичної роботи?

Навчилася створювати ефективні незмінні структури з повним набором рівності (IEquatable, Equals, GetHashCode, оператори) і додатковими методами ToString та Deconstruct. Зрозуміла практичну різницю між типами-значеннями і посилальними типами, семантику копіювання і вплив на пам'ять. На власному вимірюванні побачила, що структури швидші й економніші для великих обсягів простих даних. Освоїла, коли структура доречніша за клас, і навпаки.

## Контрольні питання

1. **Чому структури не підтримують успадкування?** Структури зберігаються за значенням і мають фіксований розмір, відомий під час компіляції. Успадкування з віртуальними методами потребує посилань і службової інформації про тип (як у класів), що несумісне з моделлю типу-значення. Структури можуть лише реалізовувати інтерфейси.

2. **Що відбувається при присвоєнні однієї структури іншій?** Створюється повна незалежна копія: усі поля копіюються по значенню. Зміна однієї змінної не впливає на іншу. У класів же копіюється лише посилання, і обидві змінні вказують на той самий об'єкт.

3. **Навіщо потрібно перевизначати GetHashCode() при перевизначенні Equals()?** Щоб зберегти узгодженість: рівні об'єкти повинні мати однаковий хеш-код. Колекції на основі хешу (Dictionary, HashSet) спочатку порівнюють хеші, і якщо рівні об'єкти дають різні хеші, вони працюватимуть некоректно.

4. **У чому перевага IEquatable<T> порівняно з Equals(object)?** IEquatable<T> дає типізований метод Equals(T), який не потребує упакування (boxing) структури в object і приведення типів. Це швидше й економніше, особливо при масовому порівнянні в колекціях.

5. **Коли виникає boxing при роботі зі структурами?** Упакування виникає, коли структура приводиться до object або до інтерфейсного типу через object (наприклад, передається у метод, що приймає object, або порівнюється через Equals(object)). При цьому створюється об'єкт у купі. IEquatable<T> та узагальнення допомагають цього уникати.

6. **Чому readonly struct є кращим вибором у більшості випадків?** Він гарантує незмінність, робить код передбачуванішим і безпечнішим, а також дозволяє компілятору уникати зайвих захисних копій при викликах методів, що покращує продуктивність.

7. **Як структури допомагають зменшити навантаження на Garbage Collector?** Структури не виділяються в купі окремими об'єктами (лежать на стеку або всередині масивів суцільним блоком), тому не створюють тисяч об'єктів, які потім треба збирати. Менше об'єктів у купі означає рідші й коротші паузи збирача сміття.
