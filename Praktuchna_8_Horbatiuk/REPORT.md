## Завдання для звіту

### 1. Які класи використовуються для роботи з файловою системою в C#? Наведіть приклади

Для роботи з файловою системою в C# використовується простір імен System.IO. Основні класи:

File - статичний клас для швидких операцій над файлами: File.WriteAllText, File.ReadAllText, File.Copy, File.Exists, File.Delete. FileInfo - об'єкт, що представляє конкретний файл і дає доступ до його властивостей (Length, LastWriteTime, Name). Directory - статичний клас для операцій над папками: Directory.CreateDirectory, Directory.GetFiles, Directory.Exists. DirectoryInfo - об'єктна версія для роботи з папкою. StreamReader і StreamWriter - потокове читання та запис тексту. Path - робота зі шляхами: Path.Combine, Path.GetFileName, Path.GetExtension.

У роботі клас FileManager використовує File, Directory, FileInfo, StreamReader, StreamWriter і Path. Наприклад, у методі CreateBackup застосовано Path.Combine для шляху, File.Copy для копіювання і DateTime для імені копії, а в CleanOldBackups через FileInfo.LastWriteTime перевіряється дата файлу.

### 2. У чому різниця між File/FileInfo та Directory/DirectoryInfo?

File і Directory - статичні класи: їхні методи викликаються без створення об'єкта і зручні для одиничних операцій (швидко записати, скопіювати, перевірити існування). FileInfo і DirectoryInfo - звичайні класи, з яких створюється об'єкт, що представляє конкретний файл або папку.

Різниця практична: якщо над одним файлом виконується одна дія, зручніше File (наприклад File.Exists). Якщо ж над одним файлом виконується кілька операцій підряд або потрібні його властивості, ефективніше створити FileInfo один раз і працювати з ним, бо статичні методи щоразу заново звертаються до файлової системи. У роботі для перегляду бекапів використано FileInfo (потрібні і ім'я, і розмір, і дата одразу), а для разових дій - статичний File.

### 3. Поясніть роботу StreamReader та StreamWriter. Коли їх краще використовувати?

StreamReader читає текст із потоку (файлу) послідовно, а StreamWriter записує текст у потік. Вони працюють з даними порціями через буфер, а не завантажують усе одразу, тому добре підходять для великих файлів або построкової обробки. StreamReader має методи ReadLine і ReadToEnd, StreamWriter - Write і WriteLine.

Їх краще використовувати, коли файл великий, коли потрібно читати чи писати построково, або коли запис відбувається поступово. Для простих разових операцій із невеликим файлом достатньо File.WriteAllText чи File.ReadAllText. У роботі SaveToText використовує StreamWriter, а ReadFromText - StreamReader, обидва обгорнуті в using для гарантованого закриття потоку.

### 4. Як працює серіалізація об'єктів через System.Text.Json? Які атрибути ви використовували?

System.Text.Json перетворює об'єкти у формат JSON (серіалізація) і назад (десеріалізація). Метод JsonSerializer.Serialize перетворює об'єкт у рядок JSON, а JsonSerializer.Deserialize відновлює об'єкт із рядка. Поведінку налаштовує клас JsonSerializerOptions.

У роботі серіалізація винесена у FileManager (SaveToJson<T> і LoadFromJson<T>) з налаштуваннями JsonSerializerOptions: WriteIndented для читабельного форматування з відступами і PropertyNameCaseInsensitive для нечутливого до регістру зіставлення імен. Замість прямої серіалізації студентів (які мають успадкування і складну структуру) застосовано окремий простий клас StudentDto з властивостями get/set: це робить серіалізацію надійною і передбачуваною, без проблем з поліморфними типами. Спеціальних атрибутів на полях не використовувалося, бо імена властивостей DTO збігаються з ключами JSON.

### 5. Які винятки можуть виникати при роботі з файлами? Як ви їх обробляли?

При роботі з файлами можливі: FileNotFoundException (файл не знайдено), IOException (загальна помилка введення-виведення, файл зайнятий), UnauthorizedAccessException (немає прав доступу), JsonException (помилка розбору JSON).

У роботі ці винятки обробляються через try/catch. Наприклад, у LoadFromJson при помилці розбору JsonException перехоплюється і перетворюється на власний зрозуміліший виняток InvalidFileFormatException. Методи меню обгорнуті в try/catch і виводять користувачу повідомлення замість аварійного завершення. Окремий пункт меню (тестування обробки винятків) навмисне намагається прочитати неіснуючий файл і завантажити зіпсований JSON, демонструючи, що обидві ситуації коректно перехоплюються і програма не падає.

### 6. Як ви реалізували резервне копіювання даних?

Резервне копіювання реалізовано у FileManager. Метод CreateBackup приймає шлях до файлу, перевіряє його існування, створює папку Backups і копіює файл туди з унікальним іменем, додаючи до назви мітку часу у форматі yyyyMMdd_HHmmss. Завдяки мітці часу кожна копія має власне ім'я і старі копії не перезаписуються.

Метод CleanOldBackups очищує застарілі копії: він проходить по файлах у папці Backups, через FileInfo.LastWriteTime перевіряє дату останньої зміни і видаляє ті, що старші за вказану кількість днів.

### 7. Які труднощі виникали під час роботи з файлами?

Перша трудність - серіалізація студентів. Студенти мають успадкування (ExcellentStudent, ForeignStudent тощо) і складну структуру, що ускладнює пряму серіалізацію в JSON. Вирішено введенням простого класу StudentDto: у нього переносяться лише потрібні поля, він серіалізується надійно, а при завантаженні з нього відновлюються повноцінні об'єкти Student.

Друга трудність - відносні шляхи. Файли створюються у робочій папці програми (поряд з виконуваним файлом у bin), а не там, де лежить вихідний код. Тому всі шляхи будуються через Path.Combine, а потрібні папки (Backups, Reports, Logs) створюються автоматично методом EnsureDirectories перед записом.

Третя трудність - гарантоване закриття потоків. Щоб потік завжди закривався навіть при помилці, StreamReader і StreamWriter обгорнуто в конструкцію using.

### 8. Що нового ви дізналися під час виконання цієї практичної роботи?

Навчилася працювати з файловою системою через класи File, FileInfo, Directory і Path, читати й писати дані через StreamReader і StreamWriter, серіалізувати об'єкти у JSON за допомогою System.Text.Json з налаштуванням JsonSerializerOptions. Зрозуміла, як коректно обробляти файлові винятки і створювати власні типи винятків. Освоїла резервне копіювання з мітками часу та очищення старих копій, а також на практиці побачила, чому відносні шляхи потребують уважності.

## Контрольні питання

1. **Чим відрізняється File.WriteAllText() від використання StreamWriter?** File.WriteAllText відкриває файл, записує весь рядок одразу і закриває його однією дією, що зручно для невеликих даних. StreamWriter дає потік, у який можна писати поступово, частинами чи построково, що ефективніше для великих обсягів або поетапного запису.

2. **Що таке серіалізація та десеріалізація?** Серіалізація - перетворення об'єкта у формат для зберігання чи передачі (наприклад, рядок JSON). Десеріалізація - зворотний процес: відновлення об'єкта з цього формату. Так об'єкт можна зберегти у файл і пізніше відтворити.

3. **Навіщо потрібен using при роботі з потоками?** Потоки тримають системний ресурс (відкритий файл). using гарантує, що потік буде закрито і ресурс звільнено автоматично, навіть якщо станеться виняток. Без цього файл міг би лишитися заблокованим.

4. **Як обробляти помилки доступу до файлів?** Операції з файлами обгортають у try/catch і перехоплюють конкретні винятки: FileNotFoundException, IOException, UnauthorizedAccessException. Це дозволяє показати зрозуміле повідомлення і продовжити роботу замість аварійного завершення.

5. **Що таке JsonSerializerOptions і для чого його налаштовувати?** Це клас налаштувань серіалізації JSON. Його налаштовують, щоб керувати форматуванням і поведінкою: WriteIndented робить JSON читабельним з відступами, PropertyNameCaseInsensitive дозволяє зіставляти імена без урахування регістру.

6. **У чому небезпека роботи з відносними шляхами до файлів?** Відносний шлях рахується від поточної робочої папки процесу, яка може відрізнятися від очікуваної (наприклад, папка з .exe у bin, а не з кодом). Через це файл може створитися чи шукатися не там, де гадає користувач. Безпечніше будувати шлях явно через Path.Combine і створювати потрібні папки.

7. **Коли краще використовувати бінарні файли, а коли текстові?** Текстові файли (JSON, CSV, TXT) зручні, коли дані мають бути читабельними для людини або сумісними з іншими програмами. Бінарні файли компактніші й швидші для великих обсягів числових даних, але не призначені для читання людиною. Вибір залежить від того, що важливіше: читабельність і сумісність чи компактність і швидкість.
